# Недочёты и предложения

Здесь перечислены ограничения текущей реализации и возможные решения. Предложения описывают будущую работу и в коде не реализованы.

## Уже исправлено

- Пустой результат `Data.Split()` больше не блокирует `Submit`: `MakeJob` создаёт пустую map результатов, помечает job как завершённую и закрывает `Done()`. Scheduler сохраняет статус `Completed`.

## 1. Нельзя отменить долгую или зависшую задачу

**Почему это проблема.** `Close()` дожидается завершения принятых jobs, но mapper и reducer не получают `context.Context`. Если callback завис или выполняется бесконечно, `Close()` будет ждать без ограничения по времени. Вызов `Close()` из самого mapper или reducer тоже приведёт к deadlock: движок будет ждать worker-goroutine, которая вызвала `Close()`.

**Предлагаемое решение.** Передавать context в обработчики и добавить `Close(ctx)` или `Shutdown(ctx)`. Описать, как отмена меняет статус job, что происходит с уже поставленными задачами и когда закрывается `Done()`.

**Пример желаемого использования:**

```go
ctx, cancel := context.WithTimeout(context.Background(), 5*time.Second)
defer cancel()

err := eng.Close(ctx) // завершить работу или вернуть ошибку по таймауту
```

## 2. Ошибки mapper и reducer не передаются в job

**Почему это проблема.** Callback-функции не возвращают `error`, у `Job` нет поля ошибки, а статус `JobFailed` нигде не устанавливается. Если callback вызывает `panic`, он происходит в worker-goroutine и без обработки приводит к остановке всего процесса.

**Предлагаемое решение.** Добавить ошибки в сигнатуры callback-ов и сохранять их в job. При ошибке остановить дальнейшие этапы, выставить `JobFailed` и гарантированно завершить `Done()`. Отдельно определить, следует ли перехватывать callback-panic или считать его фатальной ошибкой программы.

**Например, mapper мог бы возвращать ошибку:**

```go
func Map(line string) ([]contracts.Resoult[Key, int], error) {
	if line == "!invalid" {
		return nil, errors.New("invalid input")
	}
	return results, nil
}
```

## 3. Вход целиком материализуется в памяти и удерживается job

**Почему это проблема.** Контракт `Data[T]` требует вернуть `[]T`, то есть источник целиком представляется в памяти. Кроме того, `Job.Tasks` сохраняет срезы `Partition`, а `JobViewer` удерживает ссылку на job и после завершения. Пока приложение хранит viewer, входные элементы могут оставаться достижимыми для сборщика мусора.

**Предлагаемое решение.** Поддержать потоковый источник или итератор, а после map-этапа освобождать ссылки на уже обработанные входные данные.

**Пример:**

```go
view, err := eng.Submit(largeDataset, mapper, reducer)
if err != nil {
	return err
}
<-view.Done()

// Долгоживущий view удерживает Job и его map-задачи с Partition.
```

## 4. Размер map-задачи зафиксирован на 500 элементов

**Почему это проблема.** `CreateEngine` всегда передаёт в `MakeJob` размер 500. Количество элементов не всегда отражает объём работы: 500 коротких строк и 500 больших документов могут иметь разную стоимость обработки. Публичный конструктор движка не позволяет настроить размер.

**Предлагаемое решение.** Вынести размер map-задачи в конфигурацию движка и указать его единицы измерения. Для неоднородных данных позднее можно добавить разбиение по байтам или оценке стоимости.

**Например:**

```go
cfg := engine.Config{
	Mappers:          4,
	Reducers:         2,
	ShufflePartitions: 3,
	MapTaskSize:       100,
}
```

## 5. Ошибочная конфигурация приводит к `panic`

**Почему это проблема.** `CreateEngine` и `MakeJob` проверяют положительность параметров, но сообщают об ошибке через `panic`. Если значения получены из конфигурации сервиса или окружения, ошибка настройки может завершить процесс вместо того, чтобы позволить приложению вывести понятное сообщение.

**Предлагаемое решение.** Возвращать `error` из конструктора и дать вызывающему коду решить, продолжать ли запуск.

**Предпочтительный вариант API:**

```go
eng, err := engine.New(config)
if err != nil {
	return fmt.Errorf("create map-reduce engine: %w", err)
}
```

## 6. Статусы задач и `WorkerID` не отражают выполнение

**Почему это проблема.** Map- и reduce-задачи создаются со статусом `TaskPending` и `WorkerID == -1`. Worker-функции не меняют эти поля. Статус `JobFailed` также пока не используется, поэтому эти поля не позволяют надёжно наблюдать за выполнением.

**Предлагаемое решение.** Либо обновлять статус и worker ID при назначении, запуске и завершении задачи с корректной синхронизацией, либо убрать поля до появления поддержки такого состояния.

**Ожидаемый жизненный цикл:**

```text
TaskPending → TaskRunning → TaskCompleted
                           ↘ TaskFailed
```

## 7. `Load()` копирует map поверхностно

**Почему это проблема.** `Load()` создаёт новую внешнюю map, но значения типа `R` не клонирует. Если `R` содержит срез, map или указатель, вызывающий код может изменить объект, на который ссылается сохранённый результат job.

**Пример, если `R` — `[]int`:**

```go
results := view.Load()
results["a"][0] = 99 // изменит общий backing array среза
```

**Предлагаемое решение.** Для произвольного `R` библиотека не может выполнить глубокое копирование без знания его структуры. Следует явно документировать shallow-copy контракт или добавить пользовательскую функцию клонирования/требование неизменяемых результатов.

## 8. Экспортируемые имена содержат опечатки и неидиоматичный стиль

**Почему это проблема.** В публичном API используются `contracts.Resoult`, `Job.Resoults`, `Task_Mapper` и `Task_Reducer`. Их сложнее искать и использовать, а исправление после выпуска потребует миграции пользовательского кода. Ограничение `Value[V]` объявлено пустым интерфейсом и фактически не ограничивает `V`.

**Предлагаемое решение.** До стабилизации API переименовать сущности в `Result`, `Results`, `MapTask` и `ReduceTask`. Если дополнительное ограничение для значения не требуется, заменить `Value[V]` на `V any`; если требуется — определить и задокументировать конкретные ограничения.

**Например:**

```go
type Result[K Key, V any] struct {
	Key   K
	Value V
}
```

Если API уже используется внешними проектами, переименование стоит проводить с периодом совместимости и устаревшими alias-ами, если выбранная версия Go это позволяет.
