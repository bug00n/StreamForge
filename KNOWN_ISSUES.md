# Известные ограничения

Ошибки, возвращённые mapper и reducer, теперь передаются в job: она получает статус `JobFailed`, закрывает `Done()`, а исходную ошибку можно прочитать через `JobViewer.Err()`. Задачи проверяют, не завершилась ли job с ошибкой, и прекращают обработку. Эти случаи больше не относятся к известным проблемам.

## 1. Panic в callback не превращается в ошибку job

Если mapper или reducer вызывает `panic`, паника не перехватывается внутри worker. Обычная необработанная паника в goroutine завершает весь процесс, поэтому `JobViewer.Err()` не сможет сообщить её вызывающему коду.

**Предлагаемое решение:** оборачивать каждый вызов callback в функцию с `recover`, преобразовывать значение паники в ошибку и передавать её через тот же механизм `Fail`. Либо явно объявить, что callbacks не должны паниковать, и оставить panic фатальной.

```go
func callMapper[T any, K contracts.Key, V any](
	mapper func(T) ([]contracts.Result[K, V], error),
	value T,
) (results []contracts.Result[K, V], err error) {
	defer func() {
		if recovered := recover(); recovered != nil {
			err = fmt.Errorf("mapper panic: %v", recovered)
		}
	}()
	return mapper(value)
}
```

## 2. Нельзя отменить уже выполняющийся callback

После ошибки job новые mapper и reducer вызовы не запускаются, но callback, который уже выполняется, должен сам вернуться. `Engine.Close()` также ждёт остановки workers и может ждать бесконечно, если callback завис.

**Предлагаемое решение:** передавать callback-ам `context.Context`, отменять его при ошибке job или закрытии движка и документировать, что callback обязан проверять контекст. Для ограничения времени можно принимать context с deadline от вызывающего кода.

```go
type Mapper func(context.Context, string) ([]contracts.Result[Key, int], error)
```

## 3. Вход целиком материализуется в памяти

`Data.Split()` возвращает `[]T`, поэтому движок получает весь вход до обработки и удерживает его, пока живут map-задачи. Большие входы могут потребовать много памяти.

**Предлагаемое решение:** добавить потоковый интерфейс или итератор, который отдаёт элементы порциями, и планировать задачи по мере чтения.

## 4. Размер map-задачи зафиксирован

Движок всегда использует `partSize = 500`. Для тяжёлых и лёгких элементов оптимальный размер порции может отличаться.

**Предлагаемое решение:** добавить размер порции в конфигурацию `Engine` или настройки конкретной job.

## 5. Некорректная конфигурация вызывает panic

Положительность `mappersCnt`, `reducersCnt`, числа shuffle-партиций и `partSize` проверяется, но неверное значение приводит к `panic` конструктора, а не к обычной ошибке.

**Предлагаемое решение:** добавить конструктор вида `NewEngine(...) (*Engine, error)`, который возвращает ошибку конфигурации. Старый конструктор можно временно оставить для совместимости.

## 6. `Load()` копирует только внешнюю map

`Load()` создаёт копию map, но не клонирует значения типа `R` и объекты, на которые они ссылаются. Например, если `R` — структура со срезом, изменение этого среза через результат `Load()` затронет и сохранённое значение job.

**Предлагаемое решение:** оставить поверхностную копию и явно определить владение результатами в API либо позволить передать функцию клонирования `R`. Универсально глубоко копировать произвольные Go-типы без дополнительных правил нельзя.

## 7. `WorkerID` не назначается

Поле `WorkerID` у задач остаётся равным `-1`, поэтому по нему нельзя понять, какой worker обрабатывал задачу.

**Предлагаемое решение:** передавать worker ID при запуске задачи и записывать его в статус выполнения либо удалить поле, если такая диагностика не нужна.

## 8. В публичном API остались опечатки

Некоторые имена, например `Resoults` и `PutReduceResoult`, написаны с ошибкой. Исправление существующих экспортируемых имён напрямую может сломать пользователей библиотеки.

**Предлагаемое решение:** добавить корректно написанные имена, оставить старые как deprecated-обёртки, а удалить их только в следующей несовместимой версии.
