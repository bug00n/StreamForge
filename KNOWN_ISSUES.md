# Недочёты и предложения

Этот файл описывает ограничения текущей реализации и возможные направления исправления. Предложения ниже — не реализованные изменения.

## 1. Нельзя отменить зависшую или долгую задачу

**Почему это проблема.** `Close()` дожидается завершения принятых jobs, но mapper и reducer не получают `context.Context` и не могут быть остановлены. Если callback завис или выполняется бесконечно, `Close()` будет ждать его без ограничения по времени.

**Как должно быть.** Передавать context в обработчики и определить семантику отмены job: как пометить её статус, что делать с уже поставленными reduce-задачами и как гарантировать закрытие `Done()`. Для `Close` полезен вариант с таймаутом или `context.Context`.

**Пример.** Если callback ждёт внешний сервис без таймаута, то и закрытие движка может ждать бесконечно:

```go
func mapper(line string) []Result {
	response := callServiceWithoutTimeout(line)
	return parse(response)
}

view, err := eng.Submit(data, mapper, reducer)
if err != nil {
	return err
}
<-view.Done()
eng.Close() // ждёт возврата mapper
```

## 2. Пустой срез из `Split()` оставляет job незавершённой

**Почему это проблема.** Если `Split()` вернёт пустой срез, `MakeJob` создаст ноль map-задач. Тогда ни один mapper не вызовет `notifyMap`, `StartReduce` не запустится и `Done()` никогда не закроется. Пустая строка в `fixtures_wc` не воспроизводит этот случай: `strings.Split("", "\n")` возвращает один пустой элемент.

**Как должно быть.** Движок должен явно обрабатывать нулевое число map-задач: установить корректный статус job и завершить её с пустым результатом, не ожидая уведомления от worker.

**Пример входа, который сейчас зависнет:**

```go
type EmptyData struct{}

func (EmptyData) Split() []string { return nil }

view := eng.Submit(EmptyData{}, mapper, reducer)
<-view.Done() // ожидание не завершится
```

## 3. Ошибки mapper/reducer не передаются в job

**Почему это проблема.** Callback-функции не могут вернуть `error`, у `Job` нет поля ошибки, а статус `JobFailed` нигде не устанавливается. Если callback вызывает `panic`, он происходит в worker-goroutine и без обработки приводит к остановке всего процесса.

**Как должно быть.** Добавить передачу ошибок через pipeline, сохранять ошибку в job, прекращать дальнейшие этапы при ошибке и гарантированно завершать `Done()`. Для ожидаемых ошибок предпочтительны возвращаемые значения; обработку `panic` следует определить отдельно.

**Например, mapper мог бы возвращать ошибку:**

```go
func Map(line string) ([]contracts.Resoult[Key, int], error) {
	if line == "!invalid" {
		return nil, errors.New("invalid input")
	}
	return results, nil
}
```

## 4. Входные данные целиком материализуются в памяти и удерживаются job

**Почему это проблема.** Контракт `Data[T]` требует вернуть `[]T`, то есть источник сначала представляется целиком в памяти. Кроме того, `Job.Tasks` сохраняет срезы `Partition`, а `JobViewer` удерживает ссылку на job и после завершения. Пока приложение хранит viewer, входные элементы могут оставаться достижимыми для сборщика мусора.

**Как должно быть.** Для больших источников поддержать потоковое чтение или итератор. После завершения map-этапа освобождать ссылки на обработанные входные данные, если они больше не нужны.

**Пример удержания памяти:**

```go
view := eng.Submit(largeDataset, mapper, reducer)
<-view.Done()

// Если view хранится долго, связанный Job всё ещё хранит map-задачи
// и их Partition со ссылками на входные элементы.
```

## 5. Размер map-задачи фиксирован на 500 элементов

**Почему это проблема.** `CreateEngine` всегда передаёт в `MakeJob` размер 500. Количество элементов не всегда хорошо отражает объём работы: 500 коротких строк и 500 больших документов могут иметь совершенно разную стоимость обработки. Размер нельзя настроить через публичный конструктор движка.

**Как должно быть.** Вынести размер map-задачи в конфигурацию движка и описать его единицы измерения. Для источников с неодинаковыми элементами можно позднее добавить разбиение по байтам или оценке стоимости.

**Например, конфигурация могла бы задавать его явно:**

```go
cfg := engine.Config{
	Mappers: 4,
	Reducers: 2,
	ShufflePartitions: 3,
	MapTaskSize: 100,
}
```

## 6. Некорректная конфигурация приводит к `panic`

**Почему это проблема.** `CreateEngine` и `MakeJob` проверяют положительность параметров, но сообщают об ошибке через `panic`. Если числа приходят из конфигурации сервиса или переменных окружения, ошибка настройки может завершить процесс вместо того, чтобы дать приложению показать понятное сообщение или отказаться от запуска.

**Как должно быть.** Конструкторы верхнего уровня должны возвращать `error`, а вызывающий код — решать, как обработать невалидную конфигурацию.

**Предпочтительный для Go вариант API:**

```go
eng, err := engine.New(config)
if err != nil {
	return fmt.Errorf("create map-reduce engine: %w", err)
}
```

## 7. Статусы задач и `WorkerID` не обновляются

**Почему это проблема.** Map- и reduce-задачи создаются со статусом `TaskPending` и `WorkerID == -1`. Worker-функции не меняют эти поля, поэтому они не показывают реальное состояние выполнения. Аналогично, статус `JobFailed` пока не используется.

**Как должно быть.** Либо обновлять статус и worker ID при назначении, запуске и завершении задачи с корректной синхронизацией, либо убрать эти поля до появления поддержки наблюдаемого состояния.

**Ожидаемый жизненный цикл задачи:**

```text
TaskPending → TaskRunning → TaskCompleted
                           ↘ TaskFailed
```

## 8. `Load()` копирует map неглубоко

**Почему это проблема.** Метод возвращает отдельную внешнюю map, но значения типа `R` не копируются рекурсивно. Если `R` содержит срез, map или указатель, вызывающий код всё ещё может изменить объект, на который ссылается результат job.

**Пример:**

```go
results := view.Load() // предположим, R — []int
results["a"][0] = 99   // меняет общий backing array среза
```

**Как должно быть.** Для общего `R` библиотека не может безопасно выполнить глубокое копирование без знания структуры типа. Нужно явно задокументировать shallow-copy контракт либо добавить пользовательскую функцию клонирования/требование неизменяемых результатов.

## 9. Публичные имена содержат опечатки и неидиоматичный стиль

**Почему это проблема.** В экспортируемом API используются `contracts.Resoult`, `Job.Resoults`, `Task_Mapper` и `Task_Reducer`. Эти имена сложнее находить и использовать, а исправление после выпуска потребует миграции пользовательского кода. Ограничение `Value[V]` объявлено пустым интерфейсом и фактически не ограничивает `V`.

**Как должно быть.** До стабилизации API переименовать сущности в идиоматичные `Result`, `Results`, `MapTask` и `ReduceTask`. Если дополнительное ограничение для значения не планируется, использовать `V any`; если планируется — определить и описать реальные требования.

**Например:**

```go
type Result[K Key, V any] struct {
	Key   K
	Value V
}
```

При уже опубликованном API переименование следует проводить с периодом совместимости и устаревшими alias-ами, если выбранная версия Go и типы это позволяют.
